## 4. Mobile Architecture Decisions
- **Framework**: Flutter 3 (Material 3).
- **State Management**: Riverpod.
- **Routing**: GoRouter (for Role-based Route Guards).
- **Network**: Dio (with Interceptors for automatic single-flight token refresh).
- **Security**: Token storage via `flutter_secure_storage`. Zero local authority for biometric/QR validation.

## 5. Supported Mobile Features (Conceptual)
The architecture fully supports:
- Shared login (single APK).
- Backend-authoritative role parsing (Student vs Faculty).
- Protected navigation.
- Multi-step Student Face Verification & Liveness state machine.
- Dynamic QR scanning (Mobile Scanner).
- Faculty QR display & countdown loop.
- Local network connectivity configuration.

## 6. Assumptions
- The backend will provide machine-readable error codes (e.g., `qr-expired`).
- The backend will support short-polling or WebSockets for live attendance view.
- The face verification proof from the backend will be a short-lived token required for final attendance submission.
- The Cursor agent will generate the API contract before Phase 8 (Integration).

## 7. Risks
- **Blocking Dependency**: Without the API contract, true integration is blocked. If development proceeds through Phases 1-7, we will have to build against theoretical mock schemas, which guarantees breaking changes when the real API arrives.
- **Local Network TLS**: Android blocks cleartext HTTP. If the laptop backend does not have TLS, we will need to enable cleartext traffic for the testing subnet.
